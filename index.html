case-study/handytools

HandyTools: keeping heavy document jobs off the request path

Own product · built solo · in build, restricted beta · Django 6.1, DRF, Celery 5.6, Redis, PostgreSQL 17

Context

HandyTools runs OCR and PDF conversions that can take minutes on CPU-only hardware: EasyOCR (PyTorch) and Tesseract for text recognition, PyMuPDF and pdf2docx for documents. Uploads go up to 50 MB, free accounts have a daily allowance, and the whole thing runs as one Docker Compose stack on a single Hetzner server. Requests had to stay fast, and the server had to survive a bad file.

Design

  • Files stay on disk. The view stages the upload and queues only its path, so large files never pass through Redis. The job id doubles as the Celery task id.
  • Job state lives in the cache, not the database. Status is short-lived, high-churn data, so it sits in Redis with a TTL and expires on its own. PostgreSQL holds what has to last: users, plans, quotas and usage rows.
  • The browser polls. A status endpoint checks that the job belongs to the requester; the result is downloaded once and deleted after it is served.
  • Workers are configured defensively: late acknowledgement, prefetch 1, three attempts 10 s apart, soft/hard time limits of 270/300 s, concurrency 2, and a recycle after 100 tasks.
  • Cancelling is cooperative. A cache flag is checked between pages, and revoke() covers jobs that haven't started. Celery beat sweeps expired job files, orphaned media and lapsed subscriptions.

What broke: a failed job that wasn't

The task's error handler marked a job failed and then asked Celery to retry. That was a deliberate choice, so the browser's poller would stop spinning, and it turned out to be wrong in three ways:

  • The browser stops polling at failed, so a retry that succeeded was never collected.
  • A failed usage row gives the free daily allowance back, so a run that failed and then succeeded was free.
  • Users saw the raw exception text.

I caught it in a full code review on 16 October 2026, before any user reported it. The fix is a single retry-or-fail path: the job stays processing until the last attempt, only then is it marked failed with a generic message, and the details go to the logs. A regression test, test_crash_then_successful_retry_is_not_reported_failed, keeps it that way.

What broke: the A0 plot that killed a worker

On 21 October 2026 a real A0 CAD plot made a worker run out of memory. Its PDF text was glyph-coded, so text extraction found nothing usable and the job fell back to slow, tiled OCR. A worker killed by the operating system runs no except blocks, so the job sat at processing forever. I fixed it in two places:

  • A custom Celery request class whose on_failure and on_timeout hooks mark the job failed even when the task's own code never gets the chance.
  • Decoding the PDF's own font maps so the text can be read directly, which took that plot from minutes to about one second.

Result and next steps

About 700 tests run in GitHub Actions alongside ruff, mypy and a missing-migration check, and a restricted beta is open to invited engineers. Next up: wiring paid-tier priority into Celery routing (the data model exists; the routing doesn't yet) and Stripe billing.

case-study/iasmos-museum

Iasmos Culture Club Museum: a CMS built for non-technical moderators

Paid client project · built solo in ~3 months · delivered September 2026 · Django 6, SQLite, Docker, Gunicorn, Nginx

Context

The museum's moderators needed to publish exhibits, events and long bilingual history texts themselves, without technical help and without being able to break anything. Rather than bend an off-the-shelf CMS, I built a moderator dashboard around how they actually work, in Greek and English.

Hard requirements

  • Photos anchored to paragraphs. Moderators place photos beside specific paragraphs of long texts by drag and drop. The catch: Greek and English versions have different paragraph counts. One anchor index serves both languages, and an image whose anchor runs past the shorter text falls back to the gallery when the page renders.
  • Safe deletion. Moderators can delete anything; only a superuser can restore or purge.
  • Privacy by design. Self-hosted, cookie-free analytics with daily-rotating visitor hashes, consent-gated YouTube and Maps embeds, moderator Markdown sanitised with nh3, and django-axes login protection.
  • Redesign on request. The client asked for redesigns in late September, close to delivery, and the content model absorbed them.

What broke

  • Every image returned 404 (19 August 2026). After a routine pull and rebuild, all media was gone. An earlier git rm --cached media/ had deleted the files on every checkout except the machine that made the commit. I recovered all 95 files (121 MB) from git history with no data lost and wrote a recovery runbook. Media is now covered by the documented backup and restore procedures alongside the database.
  • Blank English pages (1 October). Content is written in Greek first and translated later. Untranslated fields fell back to English, which was empty. I changed the fallback to Greek, so visitors see the original text instead of a gap.
  • A hidden consent banner (31 August). Ad blockers were hiding it because of its cookie-consent naming. Renaming it to a neutral site notice brought it back.
  • Oversized images (10 October). Opaque screenshots were stored as large PNGs. Uploads now convert to JPEG unless they actually use transparency, and a compress_media management command fixed the files already stored.

Result

355 automated tests, documented backup and restore for the database and media, and a site the museum team uses daily. I maintain it on an ongoing basis.

case-study/citycare

CityCare: coordinating volunteer teams across a city's green spaces

Personal project · deploy-ready · Django 6, Python 3.13, PostgreSQL 17, Leaflet, Chart.js, Bootstrap 5.3

Context

Volunteer teams look after a city's green spaces. CityCare lets them record care, cleaning and watering work against named, geolocated places, and shows who did what, where and when. New volunteers apply through a public form, and an admin panel manages action types, places, teams and people. The interface is in Greek and English.

Design

  • A map that shows what needs attention. Each action page plots every location on a Leaflet map with OpenStreetMap tiles. Pin colour shows how recently the work was done: green within 14 days, yellow within 28, red after that. Clicking a pin opens that location's form, and admins place new locations by clicking on a map. Leaflet, Chart.js and Bootstrap are self-hosted, with no CDN dependencies.
  • Volunteer intake with an audit trail. Each application is stored as pending, accepted or declined, with who decided and when. Accepting one emails a single-use invite link that expires; signing up creates the user and their personal team in a single transaction, so a half-finished sign-up can't leave orphaned records.
  • Roles in one place. Each person has a role per team (member, team lead or moderator), plus site admins. Every view checks access through a single permissions.py module.
  • One query for the statistics. A single aggregate (TruncDay + values() + annotate(Count)) groups actions by day and team, then gets reshaped into per-team series for Chart.js, with pinch-zoom on touch screens.
  • Safe sorting. List views take sort order from query parameters, but only fields on an allowlist reach order_by.

How it evolved

  • From hardcoded choices to data. The first version had three fixed action types. They're now database rows, each with a Greek and English name, description, card image, icon, marker colour, order and active flag, and they drive the landing cards and the /action/<slug>/ pages. A data migration moved the existing records across, and the old /caring/, /cleaning/ and /watering/ URLs redirect permanently, so no links broke.
  • From SQLite to PostgreSQL. The project now targets PostgreSQL 17, and CI runs the test suite against both SQLite and PostgreSQL.

Quality

258 tests run in GitHub Actions on both databases. The project is deployment-ready; the next step is a first rollout with real volunteer teams.
